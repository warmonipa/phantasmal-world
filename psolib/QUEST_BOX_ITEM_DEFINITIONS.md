# Box item definitions

The Entity panel decodes specializable box parameters into named items and editable fields.
Its three underlying words remain the original map parameters, not inventory ItemData.
The card exposes semantic controls only; it omits raw word inputs and the redundant exact-item summary.
Changing an item or field encodes the result back into those words in one undo action.
Opening or selecting a box, or reselecting its current category/item, does not normalize its data. Field edits preserve other bits;
changing categories clears attributes whose meanings differ in the new category.

- BB Ghidra dump `original-psobb-client-source/src/Psobb.exe-05112026.c`,

- BB `box_debug_function` (line 513795) copies the same three parameters but calls

This is an important runtime distinction: the traced GC path constructs the item on the client;
the traced BB path asks the server to construct it. BB client evidence proves transmission of
the directive, not a local +1 conversion. `newserv/src/ItemCreator.cc`'s specialized-box decoder
is a separate BB server cross-check matching the GC layout; it is not evidence of BB client-side
generation. A server can change the generated result. No live game runtime test was performed.

Names come from PW's bundled BB ItemPMT and Unitxt, generated by
`:web:assets-generation:generateBoxItemCatalog`. Technique names use the client's standard
0–18 technique numbering. This catalog does not assert that every BB item exists on GC/DC.

## Random drop and Exact item

For ordinary specializable boxes (`0x0092`, the Ruins variant `0x0161`, and the CCA
variant `0x0203`), these fields form a two-stage decision. They are not mutually
exclusive Boolean switches:

1. Read **Random drop** (param1). If it is positive, use ordinary random box
   generation; **Exact item** and the item-definition words have no effect.
2. Otherwise use the specialized definition. Read **Exact item** (param3): zero
   requests category-based generation, while any nonzero value requests the
   specified item and its encodable attributes.

| Random drop (param1) | Exact item (param3) | Effective behavior |
| --- | --- | --- |
| `> 0` | Any value, ignored | Ordinary random box; its drop table can also produce no item. |
| `<= 0` | `0` | Generate an item of the configured category from the area's drop table. |
| `<= 0` | Nonzero | Generate the specified item and its encodable attributes. |

Consequently, `Random drop = 1` and `Exact item = 1` is not an invalid or conflicting
combination: ordinary random generation wins, and the latter value is inactive.
Conversely, `Random drop = 0` does not mean the box drops nothing; it enables the
specialized path. These are float parameters tested against zero, not flags that
must be exactly 0 or 1.

The category-based mode is not "the same named item with random bonuses": weapons
and tools reselect their concrete kind, armor/shield preserve their category but
regenerate subtype and bonuses, units use their own generator, and Mags reset to
the base Mag. Do not show a named Saber as a guaranteed result in this mode.

For the Stage 2 examples:

- Floor 3 / section 30's Saber +10 box has param1 `0`, param3 `1`: specified item.
- Its other six specialized boxes have param1 `0`, param3 `0`: generated categories.
- Floor 6 / section 5's Barrier, Core Shield and Shield use param1 `0`, param3 `1`;
  its random armor and weapon boxes use `0`, `0`.

The Desert crystal box (`0x038D`) is different: param1 is **Contents type**, with
`< 1` empty, `[1, 2)` ordinary random, `[2, 3)` specialized, and `>= 3` event.
These are float ranges, not equality tests. BB `DerolleEnemyHead_UpdatePhase_00677770`
compares against globals at `0x0093AFCC`, `0x0093AFC8`, `0x0093AFC4`; the matching
local Tethealla executable contains `1.0`, `2.0`, `3.0`, and its code at `0x00677770`
begins `D9 05 CC AF 93 00 D9 41 68 D8 D1 DF E0 9E 73 0F DD D9 DD D8`.
Param3 selects exact versus category-based generation only inside `[2, 3)`. Do not apply the ordinary
box's positive/nonpositive param1 test to this object.

### Proposed UI simplification (not implemented)

Replace the two numeric fields for ordinary specializable boxes with one **Drop mode**
selector. The three user-facing modes and canonical values when explicitly selected are:

| Drop mode | param1 | param3 | Relevant controls |
| --- | --- | --- | --- |
| Ordinary random | `1` | `0` | No item-definition controls. |
| Random within category | `0` | `0` | Drop category. |
| Specified item | `0` | `1` | Drop category, item selection and category-specific attributes. |

Reading an existing quest should derive the effective mode from the actual tests
above and leave its original values unchanged. Explicitly switching modes can use
the canonical values; changing both parameters should be one undoable action.
For Desert crystals, retain Empty and Event as additional modes and use contents
type 2 for both specialized modes. The current card still exposes the two numeric
fields; this section records the agreed explanation and proposed interaction only.

## Encoding

Map object record offsets are param1 `+0x28`, param3 `+0x30`, and the three words
param4 `+0x34`, param5 `+0x38`, param6 `+0x3C`. The GC unpack function reads an intermediate
directive structure; its `+0x30` input is **not** the map record's param3.

Word strings below are integer bit layouts, independent of the DAT's byte order:

| Kind | Word 1 | Word 2 | Word 3 |
| --- | --- | --- | --- |
| Weapon | `00kkssff` | `gg--aabb` | `aabbaabb` |
| Armor | `0100ssnn` | `vvff----` | ignored |
| Shield | `0101ssnn` | `vvff----` | ignored |
| Unit | `0102ssnn` | `vvff----` | ignored |
| Mag | `02kk----` | ignored | ignored |
| Tool | `03kkss--` | ignored | ignored |
| Technique | `0302lltt` | ignored | ignored |
| Meseta | `040000--` | `mmmm----` | ignored |

- Only classes 0 (weapons) and 1 (armor/shield/unit) add 1 to the encoded `kk` byte.
  The actual class uses the low nibble of word 1's highest byte.
- `ss`: subtype. `ff` in weapons: six special bits plus present/untekked flags.
  `gg`: grind. `aa/bb`: attribute type and signed percentage. S-rank custom names share
  these slots, so they are not exposed as ordinary percentage controls.
- `nn`: raw item byte 5 (armor slots for armor). `vv/ff`: raw bytes 3/4.
  DEF/EVP and unit +/- modifiers live in other inventory bytes and cannot be encoded here.
- Exact Mags preserve the type and initialize default stats; no arbitrary stats or color input.
  Random Mags are reset to the base Mag by the GC generator.
- `ll`: zero-based technique level. `tt`: technique number, **not** the level.
  Unlike regular tools, a disk's named item identity uses `tt` rather than `ll`.
  Exact stackable tools have quantity 1; the directive has no stack-count field.
- `mmmm`: unsigned amount in tens. Thus `0x007B0000` encodes 1230 Meseta.
- With param3 zero, subtype, grind, special, percentages, slots and technique identity/level
  are not fixed. In particular, the weapon and tool generators clear the input again and choose
  their own kind. Do not label such a box as a fixed Saber or Monomate.

The compact representation can fit in the map object's pre-existing three integer parameter
slots, whereas an inventory item uses a different layout and additional state. That fit is
observable. Why Sega chose this specific layout and category offset is not documented in the
code. A zero-based editor/table index translated to inventory categories is a plausible
explanation, not a confirmed historical design decision.

Tests cover these independent extracted words, category-specific layouts, signed percentages,
level/amount units, unmodified bits, semantic UI controls, and atomic undo/redo.

## Editor interaction

Item menus remain anchored in viewport coordinates, open upward when needed, and wrap
long names inside the screen. Only the list scrolls while navigating it; opening,
closing, Escape, and selecting an item must preserve the entity panel's scroll position.
Scrolling an ancestor or resizing the viewport dismisses the popup. Find item filters
names or six-digit codes without modifying quest data. A repeated category/item selection
is a no-op, including for ignored Mag or Meseta bits. A real item/field change is one undo action.

`check` includes `:web:assets-generation:verifyBoxItemCatalog` to compare regenerated
catalog data with the checked-in source. Interaction regressions cover complete mouse
press/release, Escape, keyboard selection, and popup bounds at screen edges.
